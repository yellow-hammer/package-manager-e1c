# package-manager

Расширение 1С «Менеджер пакетов»: реестр источников, каталог пакетов,
установка `.cfe`, `.epf` и `.erf` из реестра пакетов провайдера прямо
из информационной базы.

Провайдеры: **GitLab** и **GitHub**.

## Как это работает

Источник заводится **один раз**: провайдер, адрес сервера, путь проекта и,
для приватного проекта, токен. Дальше пакеты и версии читаются у того же
проекта. Прописывать ссылку на каждый пакет вручную не нужно.

```text
Источник (строка справочника)
  └── проект у провайдера
        └── пакеты              GitLab: Generic Package Registry
              └── версии        GitHub: Releases (тег + ассеты)
                    └── файлы (.cfe / .epf / .erf)
```

Если в источнике заполнено имя пакета, из проекта берется только он.

Имя package и файла `.cfe` — это свойство `Name` из `Configuration.xml`
расширения, а не имя каталога в `src/cfe`. Собранный файл:
`build/out/cfe/<Name>.cfe`.

Один package — один файл. Если в версии несколько файлов, версия
пропускается.

## Возможности

- Каталог пакетов и список версий.
- Выбор версии по semver, предвыбор новейшей, фильтр по типу релиза.
- Установка расширений `.cfe` с проверкой применимости.
- Открытие внешних обработок и отчетов `.epf` / `.erf` без сохранения на диск.
- История установок с источником, версией и файлом.
- Проверка обновлений вручную или регламентным заданием.
- Генератор шаблонов CI/CD для публикации пакетов.

Автовыбор новейшей версии — это предвыбор в списке, а не автоустановка.
Кнопку установки всегда нажимает человек. Регламентное задание только
помечает, что есть версия новее; расписание выключено по умолчанию.

## Требования

Платформа **8.3.23** и выше. Режим совместимости расширения — `8.3.23`,
поэтому расширяемая конфигурация должна работать в режиме совместимости
не ниже. Ниже 8.3.23 расширение не применяется: собственные регламентные
задания в расширениях платформа поддерживает только с этой версии.

## Токены

Публичный проект токена не требует: поле в источнике оставьте пустым.

Для приватного GitLab нужен Project Access Token или Personal Access Token
со scope `read_api`. Для приватного GitHub — токен с правом чтения
репозитория (Contents: Read). Создается в настройках проекта или пользователя.
Токен хранится только в справочнике источников, в замаскированном поле.
В код, шаблоны, коммиты, логи и скриншоты он не попадает.

Публикация из GitLab CI идет под `CI_JOB_TOKEN`, отдельный токен не нужен.
Из Jenkins нужен токен со scope `api` и credentials `gitlab-api-url`,
`gitlab-project-id`, `gitlab-package-token`.

Подробности — в справке справочника «Источники пакетов» в самой 1С.

## Публикация пакета

В расширении есть обработка «Генератор шаблонов публикации». Она подставляет
имя package, имя файла и путь сборки в шаблон GitLab, Jenkins или GitHub.
Секреты в шаблон не пишутся — только имена переменных.

Если в проекте уже есть `.gitlab-ci.yml`, сгенерированный фрагмент
сохраняют отдельно и подключают через `include`, а не кладут поверх.

## Роли

| Роль | Назначение |
| ---- | ---------- |
| Работа с менеджером пакетов | Каталог, установка |
| Чтение источников пакетов | Только просмотр источников и истории |
| Добавление и изменение источников пакетов | Заведение и правка источников |

Интерактивное удаление ни одной роли не выдается: источники помечаются
на удаление.
