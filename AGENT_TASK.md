> **Историческая часть.** Документ описывает исходную постановку. Часть решений
> с тех пор изменилась осознанно — актуальная архитектура зафиксирована в
> [doc/ARCHITECTURE.md](doc/ARCHITECTURE.md), ход работ в
> [doc/PLAN.md](doc/PLAN.md). **При расхождении верен `ARCHITECTURE.md`.**
>
> Что разошлось с этим документом:
>
> | Здесь | Как сделано |
> | ----- | ----------- |
> | Справочник хранит отдельные пакеты | Справочник хранит **каталоги**, пакеты берутся из `packages.json` |
> | `Провайдер` — строка или перечисление | Перечисление `пм_Провайдеры` |
> | GitHub и Gitea не в первой реализации | Контракт провайдера готов, реализован GitLab |
> | Semver и автовыбор новейшей версии не делаем | Сделано в `пм_ВерсииПакетов` |
> | Фоновая проверка обновлений не делается | Сделана, расписание выключено по умолчанию |
> | Обновление менеджера без предупреждения запрещено | Разрешено через двухфазное подтверждение |
> | Модуль `пм_ЗагрузчикПакетов` | Не заводился: скачивание внутри провайдера |
> | Модуль `пм_МенеджерПакетовКлиент` | Не заводился: клиентский код в модулях форм |
> | Установка через `Выполнить(МетодОбработчик)` | Явный выбор установщика по типу файла |


**Имя проекта:** `package-manager`  
**Назначение:** менеджер пакетов 1С для установки `.cfe`, `.epf`, `.erf` из внешних package/release-источников.

Документ для запуска разработки с нуля. Читать целиком перед началом работы.

---

## Контекст

Нужно создать **расширение конфигурации 1С**, которое:

1. Хранит ручной реестр источников пакетов.
2. Показывает список доступных версий пакета из выбранного провайдера.
3. Скачивает выбранный файл пакета (`.cfe`, позже `.epf` / `.erf`).
4. Для `.cfe` устанавливает или обновляет расширение в текущей информационной базе.
5. Предлагает перезапустить 1С после успешной установки расширения.
6. Умеет сформировать шаблоны CI/CD для публикации package из проекта расширения.

Провайдеры внедряются по очереди:

1. **GitLab** — первый и обязательный провайдер, основной источник в MVP: GitLab Generic Package Registry.
2. **GitHub** — второй этап, ориентир: Releases assets и подходы из `YellowPM`.
3. **Gitea** — третий этап, через отдельный провайдер после стабилизации контракта.

---

## Стандарты 1С

Разработка выполняется с учетом стандартов [yellow-hammer/dev-rules](https://github.com/yellow-hammer/dev-rules/tree/main/docs):

- новые объекты создаются руками в Конфигураторе, агент пишет BSL и CI после выгрузки;
- все добавляемые объекты метаданных получают префикс **`пм_`**;
- синонимы не содержат технический префикс;
- новые объекты добавляются в служебную/функциональную подсистему;
- для новых объектов создаются роли, интерактивное удаление у полных прав не включается;
- формы делаются управляемыми и в стиле типовой конфигурации;
- токены, host и project id не зашиваются в код.
- требования к токенам описаны отдельно в `doc/TOKENS.md` и должны быть продублированы в справке объекта настройки источника.

## Явно НЕ делать (MVP)

- Публикация на Infostart.
- Массовое обновление нескольких пакетов за один клик.
- Автоматическая фоновая проверка «есть ли новее».
- Сравнение semver и сложные правила выбора версии.
- Приватные источники без отдельного решения по безопасному хранению токена.
- GitHub и Gitea в первой реализации.
- Обновление самого `package-manager` без отдельного предупреждения.

## Референсы

### Установка `.cfe`

Репозиторий БСП на машине разработчика:

`C:\Users\ikarl\git\github.com\_yellow-hammer\ssl_3_1`

Изучить:

- `ОбщаяФорма.Расширения` → процедура `ИзменитьРасширенияНаСервере`;
- `ОбщийМодуль.ОбновлениеКонфигурации` → `УстановкаИУдалениеИсправлений`, только чтобы понять границу: патчи 1С не подходят для обычных `.cfe`.

Наш путь для обычных расширений:

- получить `ДвоичныеДанные`;
- найти расширение по имени или создать новое через `РасширенияКонфигурации.Создать()`;
- перед записью отключить предупреждения безопасности по паттерну формы `Расширения`;
- выполнить `Расширение.Записать(ДвоичныеДанные)`;
- после успеха обновить параметры работы расширений БСП, если подсистема доступна.

### `МенеджерПакетов`

Каталог `МенеджерПакетов` — главный референс для GitLab Package Registry:

- адреса строятся через `/api/v4/projects/{id}/packages`;
- `packages.json` берется из репозитория и описывает каталог пакетов;
- есть длительные операции, форма прогресса, регистр установленных пакетов;
- установка `.cfe` выполняется через `РасширенияКонфигурации.Создать()` / `Записать(ДвоичныеДанные)`.

Использовать как источник паттернов, но не копировать небезопасные решения: hardcoded token, host и project id нужно заменить настройками.

### `YellowPM`

Каталог `YellowPM` — референс для UX и будущего GitHub-провайдера:

- каталог пакетов и карточки пакетов;
- работа с `.epf`, `.erf`, `.cfe`;
- GitHub Releases как источник файлов.
- индекс пакетов: корневой `index.json` со списком chunk-файлов;
- регистр индекса пакетов и регистр установленных решений;
- UX «список пакетов» + «список файлов выбранного пакета»;
- сохранение пользовательских адресов индексов через хранилище общих настроек;
- скачивание `.epf` / `.erf` с возможностью открыть файл или добавить в дополнительные обработки;
- проверка применимости расширения перед записью.

Код не копировать без лицензионной проверки.

## Архитектура провайдеров

Провайдеры должны реализовывать единый контракт:

| Метод | Назначение |
| ---------- | ------------ |
| `ПроверитьИсточник(ИсточникПакетов)` | Проверяет доступность проекта/репозитория |
| `ПолучитьПакеты(ИсточникПакетов)` | Возвращает список пакетов источника |
| `ПолучитьВерсииПакета(ИсточникПакетов, ИмяПакета)` | Возвращает версии выбранного пакета |
| `ПолучитьФайлыПакета(ИсточникПакетов, ИмяПакета, Версия)` | Возвращает файлы версии |
| `СкачатьФайлПакета(ИсточникПакетов, ОписаниеФайла)` | Возвращает `ДвоичныеДанные` |

MVP реализует `пм_ПровайдерGitLab`. `пм_ПровайдерGitHub` и `пм_ПровайдерGitea` создаются позже, но контракт не должен быть GitLab-специфичным.

## Метаданные расширения

### Расширение

| Свойство | Значение |
| ---------- | ------------ |
| Имя расширения | `package-manager` |
| Синоним | `Менеджер пакетов` |
| Назначение | `Дополнение` |
| Префикс объектов | `пм_` |

### Подсистема `пм_МенеджерПакетов`

Функциональная подсистема для всех объектов менеджера пакетов. Включается в командный интерфейс.

### Справочник `пм_ИсточникиПакетов`

Код справочника: длина `0`. Наименование: длина `150`.

| Реквизит | Тип | Назначение |
| ---------- | ----- | ------------ |
| Наименование | Строка | Отображение источника |
| Провайдер | Строка или перечисление | `GitLab`, позже `GitHub`, `Gitea` |
| URLСервера | Строка | Например `https://gitlab.example.com` |
| ПутьПроекта | Строка | Например `group/project` |
| IDПроекта | Число | Кэш после resolve project |
| ИмяПакета | Строка | Имя package у провайдера |
| ИмяФайлаПакета | Строка | Точное имя `Something.cfe` или маска `*.cfe` |
| ИмяРасширенияВИБ | Строка | Имя в «Расширения конфигурации» |
| ТокенДоступа | Строка | Необязательный токен для приватного источника, на форме скрыть/маскировать |
| ВыбраннаяВерсия | Строка | Выбор пользователя из списка версий |
| УстановленнаяВерсия | Строка | Последняя успешно установленная версия |
| ДатаУстановки | ДатаВремя | Последняя успешная установка |
| ТекстОшибки | Строка неогр. | Последняя ошибка |

### Регистр сведений `пм_УстановленныеПакеты`

Независимый непериодический регистр для истории и текущего состояния установленных пакетов.

| Поле | Тип | Назначение |
| ---------- | ----- | ------------ |
| ИсточникПакетов | СправочникСсылка.пм_ИсточникиПакетов | Источник |
| ИмяПакета | Строка | Имя package |
| Версия | Строка | Установленная версия |
| ИмяФайла | Строка | Установленный файл |
| ДатаУстановки | ДатаВремя | Когда установлено |
| ТекстОшибки | Строка неогр. | Ошибка последней попытки |

### Общие модули

| Модуль | Назначение |
| ---------- | ------------ |
| `пм_МенеджерПакетов` | Оркестратор: источник → версия → файл → установка |
| `пм_ПровайдерыПакетов` | Единая точка выбора провайдера |
| `пм_ПровайдерGitLab` | GitLab API / Package Registry |
| `пм_ПровайдерGitHub` | Заглушка второго этапа |
| `пм_ПровайдерGitea` | Заглушка третьего этапа |
| `пм_ЗагрузчикПакетов` | Скачивание файлов пакетов |
| `пм_УстановщикРасширений` | Установка `.cfe` по паттерну БСП |
| `пм_ШаблоныПубликацииПакетов` | Формирование шаблонов CI/CD |
| `пм_МенеджерПакетовКлиент` | Клиентские команды форм |

### Обработки и формы

| Объект | Назначение |
| ---------- | ------------ |
| `пм_МенеджерПакетов` | Основной UI: каталог источников, версии, установка |
| `пм_ГенераторШаблоновПубликации` | Формирует `.gitlab-ci.yml`, `Jenkinsfile` и другие шаблоны под выбранный проект |
| Общая форма `пм_ДлительнаяОперация` | Отображение прогресса загрузки/установки |

### Роли

Создать роли по dev-rules:

- `пм_РаботаСМенеджеромПакетов` — доступ к подсистеме и основной обработке;
- `пм_ЧтениеИсточниковПакетов` — чтение источников и регистра;
- `пм_ДобавлениеИзменениеИсточниковПакетов` — изменение источников.

## GitLab API (MVP)

```http
GET /api/v4/projects/{url-encoded-path}
GET /api/v4/projects/{id}/packages?package_type=generic&package_name={packageName}
GET /api/v4/projects/{id}/packages/{packageId}/package_files
GET /api/v4/projects/{id}/packages/generic/{packageName}/{packageVersion}/{fileName}
```

Версии брать из списка packages. Файл брать из `package_files[]`, сопоставить с `ИмяФайлаПакета`.

Скачивание: HTTP GET по generic package URL или по ссылке package file, если она доступна в API.

Таймаут HTTP: 60 с. Повтор при сетевой ошибке: 1 раз.

Ошибки пользователю: 404 project/package/version, нет `.cfe` в package files, несколько файлов по маске.

## Сценарий установки

1. Проверить заполнение источника: провайдер, URL, проект, имя package, имя файла, имя расширения.
2. Получить project id, если он еще не закэширован.
3. Получить package по имени и выбранной версии.
4. Найти package file `.cfe`.
5. Скачать файл в `ДвоичныеДанные`.
6. Вызвать `пм_УстановщикРасширений.УстановитьИзДвоичныхДанных(ИмяРасширенияВИБ, ДвоичныеДанные)`.
7. При успехе записать `УстановленнаяВерсия`, `ДатаУстановки`, очистить `ТекстОшибки`.
8. Обновить `пм_УстановленныеПакеты`.
9. Вернуть клиенту флаг «нужен перезапуск».

После успеха показать вопрос: «Для применения изменений перезапустите 1С» + кнопки «Перезапустить» / «Позже».

## Шаблоны публикации пакетов

В репозитории хранить готовые шаблоны в `templates/ci/`:

```text
templates/
  ci/
    gitlab/
      package.gitlab-ci.yml
    jenkins/
      Jenkinsfile.package
    github/
      package-release.yml
    gitea/
      package-release.yml
    README.md
```

Обработка `пм_ГенераторШаблоновПубликации` должна уметь:

- выбрать целевую систему CI/CD;
- принять `PACKAGE_NAME`, `CFE_NAME`, путь к собранному `.cfe`;
- сформировать текст файла;
- вывести текст на форму и сохранить в файл через диалог;
- показать подсказку, какие переменные CI надо настроить.

Секреты и токены не генерировать в явном виде. В шаблонах использовать только переменные CI/CD.

## Критерии приемки MVP

- [ ] Проект переименован в `package-manager` в документации и манифесте.
- [ ] В 1С зафиксированы имя `package-manager`, синоним «Менеджер пакетов», префикс `пм_`.
- [ ] Созданы метаданные: подсистема, справочник источников, регистр установленных пакетов, роли, модули, обработка UI.
- [ ] В справке объекта `пм_ИсточникиПакетов` описаны публичный режим без токена и приватный режим с токеном.

- [ ] «Обновить список версий» заполняет выбор версий package.
- [ ] «Установить выбранную версию» скачивает `.cfe` и обновляет расширение в ИБ.
- [ ] Повторная установка той же версии дает понятное сообщение или явную переустановку.
- [ ] Ошибки API/отсутствия файла пишутся в `ТекстОшибки` и показываются пользователю.
- [ ] Установка идет через `РасширенияКонфигурации.Записать`, не через `УстановкаИУдалениеИсправлений`.
- [ ] Есть шаблоны `templates/ci/gitlab`, `templates/ci/jenkins`, `templates/ci/github`, `templates/ci/gitea`.
- [ ] Генератор шаблонов публикации описан в метаданных и готов к реализации.

## Заметки

- HTTP выполнять на сервере 1С.
- Не обновлять через менеджер пакетов само расширение `package-manager` без отдельного предупреждения.
- `GitLab Releases` могут быть витриной, но в MVP источник бинарей — Package Registry.
- Для GitHub и Gitea не ломать контракт провайдера, даже если API отличается.
