# Архитектура package-manager

Документ фиксирует принятые архитектурные решения. Он главнее черновых
формулировок в `AGENT_TASK.md`: при расхождении правит этот документ.

## Модель источников: гибрид «каталог + прямой пакет»

Справочник `пм_ИсточникиПакетов` хранит **каталоги**, а не отдельные пакеты.
Одна строка справочника — это один проект у провайдера, в котором лежит
манифест каталога и Package Registry с бинарями.

```text
Источник (строка справочника)
  └── packages.json          ← манифест каталога в репозитории проекта
        ├── categories[]     ← разделы для UI
        └── packages[]       ← имя, описание, категория, тип файла
              └── версии     ← из Package Registry того же проекта
                    └── файлы (.cfe / .epf / .erf)
```

Пользователь заводит источник **один раз**. Дальше новые пакеты и версии
появляются в интерфейсе сами, без ручного ввода ссылок на каждый пакет.

### Почему не «строка = пакет»

Вариант из первой редакции `AGENT_TASK.md` (каждая строка справочника —
отдельный пакет со своим URL, проектом, именем файла и именем расширения)
воспроизводит ровно ту проблему, из-за которой был отклонён подход `YellowPM`:
пользователь вручную сопровождает список ссылок. Отклонён.

### Режим «прямой пакет»

Если в проекте нет `packages.json`, источник работает в упрощённом режиме:
у строки заполняется `ИмяПакета`, каталог не читается, показываются только
версии этого одного package. Нужен для одиночных случаев и для самопроверки
источника до того, как в проекте появится манифест.

## Формат packages.json

```json
{
  "schema_version": 1,
  "categories": ["Инфраструктура", "Обмен"],
  "packages": [
    {
      "name": "package-manager",
      "description": "Менеджер пакетов",
      "category": "Инфраструктура",
      "file_name": "package-manager.cfe",
      "extension_name": "package-manager"
    }
  ]
}
```

`handler` из исходного манифеста `МенеджерПакетов` не используется:
динамическая диспетчеризация через `Выполнить(МетодОбработчик + "(...)")`
заменена на выбор установщика по типу файла.

| Расширение файла | Установщик |
| ---------------- | ---------- |
| `.cfe` | `пм_УстановщикРасширений` |
| `.epf`, `.erf` | `пм_УстановщикВнешнихФайлов` |

## Контракт провайдера

Все провайдеры реализуют одинаковый набор методов. Диспетчер —
`пм_ПровайдерыПакетов.МодульПровайдера(ИмяПровайдера)`.

| Метод | Назначение |
| ----- | ---------- |
| `ПроверитьИсточник(Источник)` | Доступность проекта, резолв и кэш ID |
| `ПрочитатьКаталог(Источник)` | Содержимое `packages.json` |
| `ПолучитьВерсииПакета(Источник, ИмяПакета, Лимит)` | Версии package |
| `ПолучитьФайлыВерсии(Источник, IDВерсии)` | Файлы версии |
| `СкачатьФайл(Источник, ИмяПакета, Версия, ИмяФайла)` | `ДвоичныеДанные` |

Очерёдность: `GitLab` (MVP) → `GitHub` → `Gitea`. Контракт не должен
содержать GitLab-специфичных понятий.

## Хранение настроек

Host, путь проекта, ID проекта и токен живут **только** в справочнике
`пм_ИсточникиПакетов`. В коде их нет. Хранилище общих настроек используется
для пользовательских предпочтений UI (лимит версий, фильтр версий, последний
выбранный источник), но не для адресов и не для токенов.

## Зависимости

| Компонент | Лицензия | Статус |
| --------- | -------- | ------ |
| Коннектор (`пм_КоннекторHTTP`) 2.4.7 | Apache-2.0 | Оставляем, заголовок сохраняем |
| БСП: длительные операции, общего назначения, строковые функции | CC BY 4.0 | Оставляем, заголовки сохраняем |
| `ОбщийМакет.пм_RegEx` (нативная компонента) | не установлена | **Удаляем**, см. ниже |
| `YellowPM` | GPL-3.0 | **Код не заимствуем**, только UX-референс |

Нативная компонента RegEx весит ~968 КБ и используется только для трёх
регулярных выражений фильтра версий. Заменяется разбором версии средствами
платформы, макет удаляется из состава расширения.

## Версии: разбор, сортировка, выбор

Разбор версии реализуется средствами платформы и заменяет нативную компоненту
`пм_RegEx`. Один парсер закрывает три задачи: фильтр по типу релиза,
сортировку и предвыбор новейшей версии.

Правила сравнения — semver:

- числовые части сравниваются численно: `1.0.10 > 1.0.9`;
- пререлиз младше релиза: `1.0.0-rc1 < 1.0.0`;
- пререлизы сравниваются поидентификаторно: `1.0.0-rc2 > 1.0.0-rc1`.

Версии, не подходящие под semver, встречаются в реальных registry (например
`package-manager-v0.1.3`). Они не отбрасываются: сортируются по `created_at`
из API и помечаются в интерфейсе как несемантические.

**Автоматический выбор новейшей версии — это предвыбор в интерфейсе, а не
автоустановка.** Кнопку установки всегда нажимает человек.

## Фоновая проверка обновлений

Регламентное задание `пм_ПроверкаОбновленийПакетов`:

- **только проверяет и помечает** «доступна более новая версия», ничего не
  скачивает и не устанавливает;
- расписание **выключено по умолчанию**, включается администратором осознанно;
- результат пишется в источник и показывается в форме менеджера.

### Ограничение платформы

Собственные регламентные задания в расширениях конфигурации поддерживаются
**только с 8.3.23**. Это требует поднять
`ConfigurationExtensionCompatibilityMode` с текущего `Version8_3_17` до
`Version8_3_23`.

**Следствие, которое надо учитывать:** режим совместимости расширения не может
быть выше режима совместимости расширяемой конфигурации. После подъёма
менеджер перестанет применяться к базам, где сама конфигурация работает в
режиме совместимости ниже 8.3.23 — а для типовых это распространённый случай.

Поэтому фоновая проверка вынесена в последний этап и остаётся отделимой:
ручная проверка обновлений (кнопка и проверка при открытии формы) работает
независимо от режима совместимости и реализуется раньше.

## Самообновление менеджера

`package-manager` собирается тем же CI и лежит в том же registry, поэтому он
виден в собственном каталоге как обычный пакет. Установка на нём перезаписывает
расширение, чей код выполняется прямо сейчас.

Самообновление разрешено, но идёт отдельным путём:

1. Явное предупреждение с описанием последствий, а не обычный вопрос об установке.
2. Запись в регистр `пм_УстановленныеПакеты` строго **до** вызова `Записать()`:
   после записи расширения обращение к собственному регистру падает с ошибкой
   «Структура таблицы несовместима с текущими расширениями».
3. Перезапуск сеанса обязателен, варианта «Позже» нет: до перезапуска сеанс
   продолжает работать на старом коде.
4. В предупреждении сказано, что при неудачном применении восстанавливать
   расширение придётся вручную через Конфигуратор.

## Шаблоны публикации

Единственный источник истины для шаблонов CI/CD — каталог `templates/ci/`.
Расширение во время работы не видит репозиторий, поэтому тексты шаблонов
переносятся внутрь расширения как общие макеты типа «Текстовый документ»:

```bash
oscript tasks/sync-ci-templates.os
```

Править макеты напрямую нельзя — синхронизация их перезапишет.

Подстановки в шаблонах помечены как `@PACKAGE_NAME@`, `@CFE_NAME@`,
`@CFE_PATH@`. Разделитель `@...@` выбран намеренно: запись `{{...}}`
конфликтует с выражениями GitHub Actions вида `${{ env.CFE_NAME }}`.

Секреты и токены не генерируются: шаблоны содержат только имена переменных
CI/CD, а что именно завести, объясняет подсказка на форме генератора.

## Роли

| Роль | Назначение |
| ---- | ---------- |
| `пм_РаботаСМенеджеромПакетов` | Работа с менеджером: чтение источников, установка пакетов |
| `пм_ЧтениеИсточниковПакетов` | Только чтение источников и истории установок |
| `пм_ДобавлениеИзменениеИсточниковПакетов` | Заведение и правка источников |

Интерактивное удаление не включено ни в одной роли: источники помечаются
на удаление, а не удаляются сразу.

## Что осознанно не делаем

- Публикация на Infostart.
- Автоматическая установка обновлений без участия человека.
- Массовое обновление нескольких пакетов одним кликом.
